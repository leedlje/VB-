# TXT 阅读器 MVP 技术方案

本方案对应 [产品设计文档](../PRODUCT_DESIGN.md)。首版仅面向 Windows 10/11 x64，离线运行，只支持本地 TXT 文件；不引入服务端、账号或数据库。

## 技术选型

| 层次 | 选择 | 用途 |
| --- | --- | --- |
| 桌面容器 | Electron | 窗口、系统文件对话框、应用生命周期和本地文件访问 |
| 开发语言 | TypeScript | 主进程、预加载脚本和阅读界面共用类型定义 |
| 阅读界面 | 原生 HTML/CSS/TypeScript | 单页阅读视图、字号控制和提示；首版不需要前端框架 |
| 构建 | Vite | 构建阅读界面；主进程和预加载脚本分别构建 |
| TXT 解码 | `iconv-lite` | 明确按 UTF-8 或 GB18030 解码，不做自动猜测 |
| 本地状态 | JSON 文件 | 保存最近打开的文件、每个文件的编码和阅读位置、字号 |
| Windows 分发 | `electron-builder` 的 NSIS 安装包 | 产出可离线安装的 x64 安装程序 |
| 测试 | Node 内置测试运行器、应用级手工验收 | 覆盖文件与状态逻辑，并验证实际阅读体验 |

依赖在开始实现时选用相互兼容的稳定版本，并提交锁文件。暂不加入 React、状态管理库、ORM 或自动更新服务。

## 应用结构

```text
src/
  main/       窗口、文件对话框、TXT 读取、状态持久化、IPC 处理
  preload/    向阅读界面暴露少量有类型的操作
  renderer/   阅读视图、字号按钮、错误与空状态
  shared/     IPC 请求与返回值、阅读状态的数据类型
tests/        文件解码、状态恢复及异常场景测试
```

主进程负责所有磁盘读写。阅读界面只调用预加载脚本提供的 `chooseFile`、`openFile`、`saveProgress`、`setFontSize` 等明确操作，不直接获得 Node.js 文件系统能力。窗口只加载随应用打包的本地页面，开启 `contextIsolation` 和沙箱，关闭渲染进程的 `nodeIntegration`；TXT 内容作为纯文本插入页面，不当作 HTML 解析。

## 关键流程

1. **打开与恢复**：用户选择 `.txt` 后，主进程检查文件是否存在、可读，再读取字节并按已保存的编码解码。启动时尝试打开上次阅读的文件；文件丢失或无法读取时显示说明和重新选择入口，不让窗口崩溃。
2. **编码切换**：新文件默认 UTF-8，识别并忽略 UTF-8 BOM；用户可手动改为 GB18030。切换时重新读取原文件、更新该文件的编码偏好，并尽可能回到原阅读位置。界面不擅自判断“乱码”或切换编码。
3. **阅读排版**：明亮主题；正文保留原换行，长行在视图宽度内自动换行。字号通过 CSS 变量调整，调整前记录可见位置，重新排版后恢复。
4. **进度保存**：以规范化的文件路径作为本地记录键，保存当前视口顶部附近的正文字符偏移，而非单纯的滚动像素值。滚动时节流保存，关闭窗口前再保存一次。重新打开时按字符偏移定位；文件内容变化后，将偏移限制在当前文本范围内，避免恢复失败。
5. **本地状态**：状态文件放在 Electron 的 `userData` 下独立子目录，包含格式版本、最近文件路径、全局字号以及逐文件的编码和字符偏移。写入失败要提示或记录错误，不能让阅读窗口退出。书籍正文不复制到状态文件。

首版以常见 TXT 文件为目标，先采用整文件读取和纯文本渲染。实现时用较大的测试文件检查打开速度与滚动流畅度；如果体验达不到要求，再考虑分块读取或分段渲染，不预先增加这部分复杂度。

## 验证与交付

自动化测试重点覆盖 UTF-8 与 GB18030 解码、BOM、空文件、文件缺失/权限错误、每个文件独立记录进度、字号变化后的恢复定位，以及损坏的状态文件。Windows 手工验收按产品文档走完整流程：打开文件、切换编码、调整字号、关闭并重启恢复，再检查长行换行与错误提示。

交付物是 Windows 10/11 x64 的离线 NSIS 安装包。打包后在干净的 Windows 环境验证安装、首次打开、重启恢复和卸载。当前阶段不做云同步、格式扩展或自动更新。
